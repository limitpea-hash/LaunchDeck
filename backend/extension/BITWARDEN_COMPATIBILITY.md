## 云端备份可行性复查（2026-11-10）

Bitwarden 云端可以保存装有导航备份文本的安全笔记，但这与网站直接调用密码管理器保存任意数据不同。当前官方支持的个人条目管理路径包括 Bitwarden 客户端、CLI，以及 CLI 托管的 Vault Management API；Public API 不管理个人保险库条目。

- [Public API](https://bitwarden.com/help/public-api/) 明确排除个人保险库条目管理。
- [Password Manager APIs](https://bitwarden.com/help/bitwarden-apis/) 的 Vault Management API 需要通过 CLI 的 `serve` 启动本地服务。
- [CLI](https://bitwarden.com/help/cli/) 支持创建 type=2 的安全笔记、读取条目及同步，可以设计按需运行的上传/下载工具，无需常驻 `serve`；网页或扩展按钮仍需另行安装本机桥接程序才能调用本机 CLI，不能直接执行系统命令。
- [导入说明](https://bitwarden.com/help/import-data/) 支持导入文件；数据在客户端加密后上传。重复导入不会去重，不能把导入包装为原条目的自动更新。
- 同一导入说明指出 Notes 的最大加密字段长度为 10000，原文经过 Bitwarden 加密可能增加30–50%。不能把可保存的原文长度直接设成10000；应为外层加密、段编号与校验信息预留空间，保守按每段6000个ASCII正文字符设计并在实际客户端验证。

最新官方 clients 源码固定提交为 `15b835e1efc9e0903cd52f901f57cbae197a403f`。再次检查[凭据客户端](https://github.com/bitwarden/clients/blob/15b835e1efc9e0903cd52f901f57cbae197a403f/libs/common/src/platform/services/fido2/fido2-client.service.ts)与[认证器接口](https://github.com/bitwarden/clients/blob/15b835e1efc9e0903cd52f901f57cbae197a403f/libs/common/src/platform/abstractions/fido2/fido2-authenticator.service.abstraction.ts)，仍没有 largeBlob 保存/读取处理；创建响应只含 credProps，认证映射的 extensions 为空。此前的通行密钥自动备份方案仍不满足启用条件。

本地实验使用纯合成的网站、页面、网站位置及 Dock 固定标记，无用户数据：JSON → gzip → AES-256-GCM → Base64 文本，再反向恢复。各样本字节一致，篡改后认证失败，受限解压会拒绝超限输出。

待用户选择后实施：

1. 压缩加密文本：复制后在 Bitwarden 安全笔记中保存，恢复时粘贴；无需配套服务，需要手动保存，大数据分段。
2. Bitwarden兼容导入文件：生成包含一个或多个安全笔记的导入JSON，用户在Bitwarden导入；无需配套服务，重复导入会产生新条目。

保持既有完整JSON备份行为。新导航备份范围仍仅为网站、分类/页面、文件夹、排列与Dock；混排只记录小组件位置标识，不带正文、壁纸或定位资料。未获选择前不新增运行时依赖、权限或云端写入逻辑。

## 结论

### 分页通行密钥实验（2026-11-10）

按用户新要求，增加独立实验 `backend/experiments/passkey-pages/`，每个合成页面创建一个discoverable credential，通过largeBlob写入、读回，并通过选择器读取分页。此项选择仅授权实验，不代表已证明Bitwarden云端可用。

实验页 `http://localhost:3007/` 已在Chrome与内置浏览器确认加载，默认不发起任何凭据请求。用户确认当前尚未安装或登录Bitwarden；Chrome当前配置的扩展菜单也未看到Bitwarden。因此未执行真实凭据创建、保险库写入或跨设备恢复，等待安装与解锁后继续。

自动化模拟覆盖分页独立恢复、required能力声明、忽略扩展时拒绝成功、写入必须written=true、导入读回与内容校验、损坏/超限/压缩炸弹拒绝、只监听本机且拒绝异源Host与数据API。完整回归133项通过，其中新增6项。模拟提供者成功仅证明实验程序判定逻辑，不作为Bitwarden支持证据。

两个合成页面压缩封装后各约330–350字节，即使只有一至两个网站，也超过userHandle上限64字节。[WebAuthn规范](https://www.w3.org/TR/webauthn-3/#user-handle)将其定义为账号标识；分页无法取代缺失的largeBlob能力。导入选择凭据本身也不返回账号显示名里的任意备份内容。此实验不复用名称、userHandle或PRF作为页面存储。

本轮不启用“通过 Bitwarden 通行密钥自动保存与恢复导航备份”。当前检查到的 Bitwarden 浏览器客户端没有将 WebAuthn `largeBlob` 接入保存 / 读取路径。成功保存普通通行密钥不能作为导航备份成功的依据。

## 可复查证据

固定核验版本：Bitwarden clients 提交 `d63a79cf2f1d222d10e8d3f0253ca65b050eb192`。

- [浏览器凭据客户端](https://github.com/bitwarden/clients/blob/d63a79cf2f1d222d10e8d3f0253ca65b050eb192/libs/common/src/platform/services/fido2/fido2-client.service.ts)：注册结果仅返回 `credProps` 扩展；认证参数映射将扩展设为空对象，未处理 `largeBlob` 请求及其结果。

- [WebAuthn 标准](https://www.w3.org/TR/webauthn-3/#sctn-large-blob-extension)：`largeBlob` 为可选能力；必须分别确认支持、写入成功与读回一致。浏览器整体支持、PRF 支持、凭据创建成功都不能代替这些检查。

以上是固定版本源码核验。已检查内置浏览器及当前可控的 Chrome 配置，后者扩展菜单未安装 Bitwarden；未切换用户的其他浏览器配置或安装并登录新保险库。未创建真实保险库条目，也未进行实际 Bitwarden 双设备保存 / 恢复测试。不将此结果描述为已完成真机测试。

## 后续启用条件

只有在指定 Bitwarden 版本和受支持的网页来源中，确认 `largeBlob.supported`、`written`、完整字节读回，以及第二设备恢复均成功，才可启用该备份途径。必须检查提供凭据的实际密码管理器；系统认证器成功不能归因于 Bitwarden。不得将备份塞进通行密钥名称、用户名或用户标识字段。

验证应使用合成数据，不能上传用户现有导航或索取保险库主密码。任何保存失败、取消、容量不足或校验失败都不能修改现有布局。已有本地 JSON 备份导入导出继续保留；本次没有擅自改成 CLI 常驻服务或第三方云同步。
